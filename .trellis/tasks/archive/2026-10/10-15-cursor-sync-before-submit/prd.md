# 提交前 Cursor 同步配置

## 目标与用户价值
让用户可选择在 TokChan 发起的上传之前显式同步 Cursor 用量，降低 submit 内部短超时使用旧缓存、遗漏近期用量的风险，同时保持未开启用户的既有行为。

## 已确认背景
用户通过 npx 最新 Tokscale 执行 `cursor sync --json` 成功（synced=true, rows=7046, error=null），但随后 submit dry-run 在请求第 11 页触及 15 秒预算，回退缓存；输出仍包含 Cursor 用量，不能描述为完全未包含 Cursor。此前全局安装的 4.15.0 检查不代表 TokChan 的配置环境。

仓库入口与证据汇总见 `research/entry-points-and-contract.md`。用户已同意默认关闭、覆盖手动提交和立即运行自动提交、同步失败停止提交、明确不覆盖外部定时调度的范围。

## 需求

### R1 — 持久化开关
常规设置的 Agent 连接附近新增“提交前同步 Cursor”开关，默认关闭，即时保存，不依赖自动提交页的“应用”。跨重启保留，升级缺失键时关闭，清空 TokChan 配置时恢复关闭。切换开关本身不发起 CLI/API 请求，也不改 Tokscale 的设置。
证据：`TokChan/Shared/Services/PreferencesStore.swift:11-66,85-160`；`TokChan/Features/Settings/SettingsView.swift:254-273`；偏好归一化重建位置 `TokChan/Features/Dashboard/DashboardViewModel.swift:1329-1344`。

### R2 — 覆盖所有 TokChan 显式上传入口
开启后，首次提交、面板在线刷新、状态菜单提交并刷新、设置中“立即运行自动提交”均先同步 Cursor，再执行原上传动作及其后续读取；本地模式下主动点击在线提交菜单也遵守该策略。沿用设置中的 npx 和版本选择，禁止改用全局 tokscale。若填具体版本则两步均使用该版本；latest 仍是原来的动态版本选择，不承诺不可变包解析。
证据：`TokChan/Shared/Services/TokscaleCLIClient.swift:26-48`；`TokChan/Features/Dashboard/DashboardViewModel.swift:564-604,611-614,630-659,684-708,1286-1294`。

### R3 — 验证同步结果，失败不上传
仅当同步进程成功、JSON 格式可识别、synced=true、rows 为非负整数且没有 error 时继续。零条记录可正常继续；部分账号失败、格式异常、命令不支持、超时或进程失败均停止该次上传，不再刷新统计/自动提交状态，保留显示缓存与读取时间，并在原操作反馈处提示“Cursor 同步失败，未提交用量”及可重试信息。不得只依赖退出码，也不得静默降级到旧缓存上传。
证据：用户成功 JSON 与超时日志；`TokChan/Shared/Services/TokscaleCLIClient.swift:438-440,533-535` 现有上传方法丢弃成功输出；历史上游 JSON 同步失败仍可能正常退出，详见研究文件。

### R4 — 作用范围、等待与隔离
设置说明必须明确“仅影响 TokChan 发起的提交和立即运行自动提交，不影响 Tokscale 定时自动提交”，并说明同步失败不会提交。等待沿用现有操作忙碌反馈，全程禁止重复/冲突操作；开启配置后即使自动提交筛选不含 Cursor，也先执行同步。同步等待期间发生账号或 CLI 上下文变化，或任务取消，不得继续上传或把旧结果发布给新上下文。关闭面板保持原来的继续执行和提示抑制行为。
证据：`TokChan/Features/Dashboard/DashboardViewModel.swift:41-58,630-659,684-708`，以及研究文件中的异步边界分析。

## 验收标准

| 编号 | 可观察结果 | 需求 |
|---|---|---|
| AC1 | 无新键及关闭时行为一致，上传链路零次显式 Cursor 同步；保存、归一化、重启、清空均正确 | R1、R2 |
| AC2 | 所有上传入口开启时严格先一次同步、再一次原上传、再原后续读取，使用相同配置的 npx/版本 | R2 |
| AC3 | 非零退出、超时、synced=false、非空/非 null 错误、无效 JSON 均零上传、零后续读取且可重试；零行成功可继续 | R3 |
| AC4 | 同步期间保持忙碌，重复点击不重复启动；账号/CLI 上下文变更或取消后不上传；面板关闭不取消显式工作 | R4 |
| AC5 | 设置有明确作用范围说明，开关即时保存且不触发外部操作；未改变自动提交页应用语义 | R1、R4 |
| AC6 | 定时 autosubmit、后台刷新/唤醒、本地 graph、纯统计刷新、Cursor 登录/状态、价格检查及自动提交配置/禁用均不新增显式同步 | R2、R4 |

## 不在范围内
- 修改 Tokscale 本身的超时或分页逻辑、向上游发 PR、改写/替换其调度器。
- 增加自建定时任务、独立“立即同步”按钮、可配同步超时、自动重试或强制升级 CLI。
- 直接读取/写入 Cursor 凭据或缓存文件，改 Tokscale scheduler/settings。
- 全面重构成功退出时的所有 CLI 警告展示，或改变原有本地/在线数据模式。

## 风险与延后事项
显式同步增加等待时间，上传命令仍可能再次隐式同步并超时后使用刚生成的缓存；本功能不保证提交时刻服务端数据绝对完整，也无法隔离外部 CLI 对缓存的并发写入。沿用现有每命令 300 秒进程超时，超过时安全停止，后续是否提供更长预算另行讨论。旧版本不支持 JSON 同步时明确报错；关闭开关恢复原行为。

用户在最终规划摘要后回复“开始”，批准实施；功能已获批准提交为 `b2678b7`。实现、独立审查及单元/构建验证已完成。UI 自动化受 SystemUIServer 可见性限制而跳过，不计为通过；用户已对本地验收版反馈“没问题，继续后续流程，记得记录fragment”，人工验收完成。详见 `verification.md`；待完成发布片段及归档、journal 收尾，不推送或发布。
