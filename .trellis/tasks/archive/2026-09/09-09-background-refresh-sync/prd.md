# 统一后台刷新与提交状态

## Goal

让 TokChan 在应用运行但菜单面板关闭时也能持续更新菜单栏统计，并用一致、明确的操作语义区分线上统计读取、本地用量提交和自动提交状态查询。

## Background

当前完整统计快照以 5 分钟为新鲜度窗口，每次从公开 API 并行读取 all、week、month，并由 week 派生 day，四个范围整批成功后才发布。刷新定时器目前由 `DashboardViewModel.panelDidAppear()` 启动、`panelDidDisappear()` 停止，因此面板关闭期间菜单栏标题只显示旧缓存。

静默统计刷新只读取线上数据。Tokscale 自动提交由外部 `launchd` 任务管理，TokChan 不会收到完成通知。自动提交状态查询会启动 `npx`/Node，成本高于 HTTP 统计读取。

现有手动入口语义不统一：Dashboard 刷新按钮执行“提交后读取”，右键“立刻推送”只提交，右键“立刻拉取”只读取。相关证据和设计审查见 `research/background-refresh-architecture.md` 与 `research/background-refresh-design-review.md`。

## Requirements

- R1：应用运行期间，无论菜单面板是否打开，完整统计快照均采用统一的 5 分钟新鲜度窗口；到期后自动只读拉取并更新菜单栏统计。
- R2：后台自动动作不得执行 `submit`、`autosubmit run`、自动提交配置或其他隐式上传。上传只来自 Tokscale 自动提交或用户明确操作。
- R3：所有统计触发继续复用完整批次、原子发布、请求合并、账号与 generation 隔离、失败保留旧数据等现有一致性保证；不得新增第二套请求状态机。
- R4：应用启动时立即按缓存年龄评估一次；系统唤醒时只重新评估一次，不补跑睡眠期间错过的周期。自动失败采用 30 秒、1 分钟、5 分钟并封顶 5 分钟的分级退避，任一成功后重置；用户主动读取绕过退避。
- R5：面板开关只管理展示与操作反馈生命周期，不创建、停止或复制统计调度器。macOS App Nap 或系统调度可延后执行，因此“五分钟”表示应用获得执行机会时以成功读取时间为基准重新评估，不承诺硬实时。
- R6：取消“只推送、不刷新”的用户入口。所有用户主动提交均在成功后强制读取一个新的完整统计批次；另保留明确的“仅刷新线上统计（不上传）”操作。
- R7：用户可从可见文案、帮助文本和无障碍标签判断操作是否上传。统计时间只能表述为“最近成功读取”，不得暗示提交结果已经被服务端统计处理。
- R8：自动提交状态采用事件驱动查询，只在应用启动、Settings 窗口每次从不可见变为可见、配置成功、立即运行成功、状态手动重试，以及 npx/版本上下文改变后触发；同一段连续可见期间只查询一次，不加入 5 分钟统计轮询，也不因 Dashboard 面板开关触发。
- R9：统计和自动提交状态保持独立失败边界与独立时间戳；任何一方失败都不得撤销另一方的成功结果。
- R10：用户提交或立即运行期间若账号、npx 或 Tokscale 版本改变，旧操作不得为新上下文发起后续读取或发布结果。

## Acceptance Criteria

- [ ] AC1（R1、R5）：应用保持运行且 Dashboard 从未打开或已经关闭时，成功快照满 300 秒后至多触发一个完整统计批次，成功后菜单栏标题自动更新。
- [ ] AC2（R2）：应用启动、后台 deadline、面板开关和系统唤醒路径的记录中不存在 submit、run、configure 或 disable 命令。
- [ ] AC3（R3、R5）：后台统计调度幂等且全应用只有一个；反复打开/关闭面板不改变调度器数量或制造重复请求。
- [ ] AC4（R3、R6、R10）：普通自动触发合并到当前批次；用户提交先废弃提交前批次，提交成功后读取新批次；旧账号或旧上下文结果不能覆盖当前状态。
- [ ] AC5（R4）：fresh 状态唤醒不请求；stale 且不在自动退避窗口内时至多请求一个批次，在退避窗口内时零请求；跨越多个周期也不补跑。后台自动失败按 30 秒、60 秒、300 秒退避并在成功后复位。
- [ ] AC6（R3、R4）：后台失败保留旧菜单栏与面板数据及旧统计读取时间；用户“仅刷新线上统计”可立即绕过自动退避。
- [ ] AC7（R6、R7）：右键菜单不再出现只推送动作，而是提供“提交本地用量并刷新统计”和“仅刷新线上统计（不上传）”；Dashboard 上传入口及自动提交立即运行入口明确提示会上传。
- [ ] AC8（R6、R7）：提交失败时不读取统计；提交成功但读取失败时保留旧快照，并明确反馈“已提交但读取失败”；读取成功只表示统计读取完成，不承诺包含刚提交的数据。
- [ ] AC9（R8、R9）：自动提交状态只在列出的事件触发；Settings 新建或从不可见重新前置各查询一次，同一段连续可见期间不重复；5 分钟 tick 与 Dashboard 开关不查询状态。状态失败不阻塞统计，统计失败不删除旧状态。
- [ ] AC10（R7、R9）：`fetchedAt` 只由成功完整统计批次推进，`autosubmitObservedAt` 只由成功状态查询推进；右键菜单继续动态显示最近成功统计读取时间。
- [ ] AC11：新增确定性测试覆盖关闭面板后台更新、启动与唤醒、分级退避、触发合并、手动操作竞态、上下文切换、事件驱动状态查询及无隐式上传。

## Out of Scope

- 替代或修改 Tokscale 的 `launchd` 自动提交机制。
- 自建本地用量扫描、统计引擎或 TokChan 后台上传机制。
- 修改 Tokscale 服务端 API 或依赖服务端推送通知。
- 提供用户可配置的 TokChan 统计刷新频率。
- 保证应用被系统挂起、退出或电脑睡眠时仍严格每 300 秒运行。

## Compatibility and Risks

- 每个成功完整批次产生 3 个 HTTP 请求；5 分钟全天运行理论上约 864 个请求。该频率是用户确认的数据新鲜度取舍。
- 服务端没有提交完成后立即可见的契约，因此提交后的读取可能仍返回旧聚合结果。
- 本需求有意取代 `.trellis/spec/macos/data-persistence.md`、`swiftui-guidelines.md`、`tokscale-integration.md`、`testing-guidelines.md` 中“隐藏面板停止刷新”和“右键推送只 submit 不 fetch”的旧合同；实施完成后必须同步这些规范。
