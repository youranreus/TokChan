# 本地缓存与统一静默刷新策略

状态：已实施并完成自动化验证。

## 目标
让 TokChan 在已有历史数据时打开即可阅读，更新过程安静，四个统计范围保持同批更新。

## 背景
当前已持久化多范围展示缓存，但有缓存即不请求；手动按钮先提交本地用量，仅重读当前范围。缓存时间未参与新鲜度判定。代码证据、既有契约和外部依据见 research/cache-refresh.md。

## 已确认需求
以下产品决策均在 2026-09-06 对话中确认。

| ID | 要求 |
| --- | --- |
| R1 | 打开立即展示同账号上次保存的数据；过期只触发更新，不清空内容。首次安装、首次使用新账号或缓存损坏且无有效备份时允许真实加载/失败态，不伪造数据。 |
| R2 | 全部、今日、本周、本月全部获取成功后一起替换；任一统计请求失败，整组保留上一份完整数据。 |
| R3 | 静默刷新只读取线上统计，不提交本地用量。现有 autosubmit 和手动提交行为保留；手动提交成功后改为刷新全部范围。 |
| R4 | 新鲜度窗口 5 分钟；打开先展示缓存，过期后后台刷新；面板持续打开时每 5 分钟刷新，关闭后停止定时轮询。 |
| R5 | 自动提交状态独立更新或报错，不阻塞四个统计范围；失败可保留旧状态。 |
| R6 | 低调显示“更新于…”；跨日旧数据标明实际日期。后台成功不弹提示，失败不展示醒目横幅，详细错误通过轻量入口查看。 |

## 技术约束
- 只保存映射后的展示数据与观察到的状态，不保存原始会话、凭据或作为配置真源。
- 保持 macOS 13、原生 SwiftUI 菜单栏界面、现有尺寸及范围切换行为。
- 用服务端 dateRange 解释统计日期，不按本地时区重新计算今日用量。
- 批次与账号隔离；切换范围只是展示选择，不中断整组请求。
- 采用带版本的 JSON 快照和原子文件写入，详见 design.md；写入失败不丢失原文件，不否定已成功的线上读取。

## 验收标准
| ID | 对应要求 | 可观察结果 |
| --- | --- | --- |
| AC1 | R1 | 同账号有效快照在冷启动/重开时先于网络完成展示；离线仍可阅读；无缓存不显示虚构零值或其他账号数据。 |
| AC2 | R1、R2 | 完整缓存下四范围立即切换，不触发独立范围请求；批次中途无部分新统计发布，任一统计失败则整组保持旧版。 |
| AC3 | R4 | 未满 5 分钟重复打开无冗余统计请求；过期打开只启动一批；持续打开每 5 分钟刷新，关闭后无新定时请求。 |
| AC4 | R3 | 所有静默触发都没有 submit/run 操作；手动提交成功后全组重读，提交失败不报告刷新成功，提交成功但读取失败可区分。 |
| AC5 | R2、R4 | 重复触发合并；旧账号/旧批次响应不能覆盖当前快照；刷新中切换范围不取消整组获取，保持用户选择。 |
| AC6 | R5 | CLI 状态读取失败保留旧状态并独立记录错误；四范围读取成功仍发布新统计。 |
| AC7 | R6 | 有缓存时静默刷新不清屏、不弹成功或醒目错误横幅、不使提交按钮旋转；最后获取时间可见，跨日旧数据有实际日期，错误可点开查看。 |
| AC8 | R1、R2 | 新旧格式迁移、损坏文件、原子写失败均可恢复或回退；写失败保留旧磁盘数据且允许内存更新，重启恢复实际成功保存的数据。 |

## 范围外
自建本地用量计算引擎、替代 Tokscale autosubmit、额外后台上传、修改远端 API、数据库或通用缓存框架。关闭面板后不安排常驻轮询，也不新增刷新频率设置项。

## 风险与边界
- 全组策略受最慢/失败的统计请求制约，这是已确认的一致性取舍。
- 三个远端响应没有已验证的共同版本契约；一次发布保证客户端整组替换，不承诺远端严格同一时刻。
- 线上读取不保证包含尚未上传或尚未被远端处理的用量。
- 从旧格式迁移时保留已有范围供阅读，但缺失范围仍需首次成功获取；旧缓存不被伪装成完整新批次。
